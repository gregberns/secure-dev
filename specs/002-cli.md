## Overview

This spec defines the command-line interface for `sd` (secure-dev), including command structure, flags, output formatting, error handling, shell completions, and exit codes. The CLI is the primary user-facing surface of the tool and must be non-interactive by default, machine-parseable via `--json`, and organized into logical command groups. The implementation uses Cobra and Viper, following one-file-per-command conventions in `internal/cmd/`.

## Goals

- G1: Define the complete command tree, including all subcommands, flags, and aliases
- G2: Establish output conventions (human-readable on stderr, structured JSON on stdout)
- G3: Define exit code semantics so scripts and agents can reliably interpret results
- G4: Specify Cobra configuration patterns (prefix matching, command groups, persistent hooks)
- G5: Ensure every command is non-interactive by default and fully automatable
- G6: Provide shell completion support for bash, zsh, and fish

## Non-Goals

- NG1: Defining VM backend internals (covered by a separate backend spec)
- NG2: Defining provisioning module content or format (covered by spec 006)
- NG3: Defining SSH key management or session multiplexing internals
- NG4: Specifying the configuration file schema beyond what the CLI needs to read/write it
- NG5: GUI or TUI interfaces

## Requirements

### REQ-002-001: Command Entry Point

The CLI binary MUST be named `sd`. The entry point MUST be `cmd/sd/main.go`, which calls `internal/cmd.Execute()`. The root command MUST print help text when invoked with no arguments.

**Acceptance criteria:**
- [ ] `cmd/sd/main.go` exists and calls `internal/cmd.Execute()`
- [ ] Running `sd` with no arguments prints help and exits with code 0
- [ ] The root command short description is "Manage secure VM environments for AI coding agents"

### REQ-002-002: Command Groups

Commands MUST be organized into the following groups, displayed with headers in help output:

1. **VM Management**: `create`, `destroy`, `start`, `stop`, `list`, `status`, `snapshot`
2. **Connection**: `connect`, `exec`, `sync`, `ssh-config`
3. **Configuration**: `config` (with subcommands `set`, `get`, `list`, `edit`, `validate`, `egress`)
4. **Provisioning**: `provision` (with subcommands `list`)
5. **Security**: `token` (with subcommands `github setup`, `rotate`, `revoke`, `list`), `audit`, `security` (with subcommand `status`), `diff`
6. **Diagnostics**: `doctor`, `version`, `logs`
7. **Utility**: `completion`

**Acceptance criteria:**
- [ ] `sd help` output displays commands under group headers
- [ ] Group headers are visually distinct (colored or bold) in terminal output
- [ ] Every command listed above is registered and reachable

### REQ-002-003: VM Management Commands

The following VM management commands MUST be implemented:

| Command | Syntax | Description |
|---------|--------|-------------|
| `create` | `sd create <name> [flags]` | Create a new VM with the given name |
| `destroy` | `sd destroy <name> [flags]` | Destroy a VM and its resources |
| `start` | `sd start <name>` | Start a stopped VM |
| `stop` | `sd stop <name>` | Stop a running VM |
| `list` | `sd list [flags]` | List all managed VMs |
| `status` | `sd status [name]` | Show status of one or all VMs |
| `snapshot` | `sd snapshot <subcommand> <name>` | Manage VM snapshots |

`sd create` MUST accept these flags:
- `--backend <name>` (default: `lima`) -- VM backend to use
- `--cpus <n>` (default: backend-specific) -- number of CPUs
- `--memory <size>` (default: backend-specific) -- memory allocation (e.g., `4GiB`)
- `--disk <size>` (default: backend-specific) -- disk size (e.g., `50GiB`)
- `--modules <module,...>` (repeatable or comma-separated) -- provisioning modules to apply after creation
- `--mount <host:guest[:mode]>` (repeatable) -- mount a host directory into the VM (default mode: `ro`; specify `:rw` for read-write)
- `--allow-egress <domain>` (repeatable) -- add a domain to the VM's egress allowlist

`sd destroy` MUST accept:
- `--force` / `-f` -- skip confirmation (required for non-interactive use)

`sd snapshot` MUST support subcommands:
- `sd snapshot create <vm> --tag <tag>` -- create a named snapshot
- `sd snapshot list <vm>` -- list snapshots for a VM
- `sd snapshot restore <vm> --tag <tag>` -- restore a snapshot
- `sd snapshot delete <vm> --tag <tag>` -- delete a snapshot

**Acceptance criteria:**
- [ ] All commands above are registered and accept the specified flags
- [ ] `sd create myvm` creates a VM using the default backend
- [ ] `sd create myvm --backend lima --cpus 4 --memory 8GiB` passes all flags to the backend
- [ ] `sd create myvm --modules claude-code,docker` provisions the specified modules after creation
- [ ] `sd create myvm --mount ~/project:/project` creates a read-only mount
- [ ] `sd create myvm --mount ~/project:/project:rw` creates a read-write mount
- [ ] `sd create myvm --allow-egress custom.example.com` adds the domain to the egress allowlist
- [ ] `sd destroy myvm` without `--force` exits with an error explaining `--force` is required for non-interactive use
- [ ] `sd snapshot create myvm --tag clean` creates a snapshot tagged "clean"

### REQ-002-004: Connection Commands

The following connection commands MUST be implemented:

| Command | Syntax | Description |
|---------|--------|-------------|
| `connect` | `sd connect <name>` | SSH into the VM and attach to a tmux session |
| `exec` | `sd exec <name> -- <command>` | Execute a command inside the VM |
| `sync to` | `sd sync to <vm> <src> [<dst>]` | Sync files from host to VM |
| `sync from` | `sd sync from <vm> <src> [<dst>]` | Sync files from VM to host |
| `ssh-config` | `sd ssh-config <name>` | Print the SSH config fragment for a VM |

`sd connect` MUST:
- Establish an SSH connection to the named VM
- Attach to or create a tmux session inside the VM
- Accept `--no-tmux` to skip tmux attachment

`sd exec` MUST:
- Execute the command after `--` inside the VM via SSH
- Stream stdout and stderr to the caller
- Exit with the remote command's exit code

`sd sync to` MUST:
- Copy files from the host into the VM using rsync or equivalent
- If `<dst>` is omitted, default to `~/<basename of src>` inside the VM

`sd sync from` MUST:
- Copy files from the VM to the host using rsync or equivalent
- If `<dst>` is omitted, default to `./<basename of src>` on the host
- Accept `--diff` to preview differences without copying

`sd ssh-config` MUST:
- Print the SSH config fragment for a VM to stdout
- Support `--json` to output the config as a JSON object with individual fields

**Acceptance criteria:**
- [ ] `sd connect myvm` opens an SSH session with tmux
- [ ] `sd connect myvm --no-tmux` opens a plain SSH session
- [ ] `sd exec myvm -- uname -a` prints the VM's kernel info and exits with code 0
- [ ] `sd exec myvm -- false` exits with code 1
- [ ] `sd sync to myvm ./src /home/user/project/src` syncs files into the VM
- [ ] `sd sync from myvm /home/user/project/src ./src` syncs files from the VM
- [ ] `sd sync from myvm /path --diff` previews differences without copying
- [ ] `sd ssh-config myvm` prints a valid SSH config fragment to stdout
- [ ] `sd ssh-config myvm --json` outputs config fields as JSON

### REQ-002-005: Configuration Commands

The `config` command MUST support the following subcommands:

| Command | Syntax | Description |
|---------|--------|-------------|
| `config set` | `sd config set <key> <value>` | Set a configuration value |
| `config get` | `sd config get <key>` | Get a configuration value |
| `config list` | `sd config list` | List all configuration values |
| `config edit` | `sd config edit [--project]` | Open the config file in `$EDITOR` |
| `config validate` | `sd config validate` | Validate all discoverable config files |
| `config egress` | `sd config egress <subcommand>` | Manage per-VM egress allowlist |

Running `sd config` with no subcommand MUST print help for the config command group.

`sd config set` MUST support dotted key paths (e.g., `defaults.backend`, `defaults.cpus`).

`sd config get` MUST print only the value to stdout (no labels, no formatting) so it can be used in scripts.

`sd config edit` MUST open the user-level config file in `$EDITOR` (or `$VISUAL`, falling back to `vi`). It accepts `--project` to edit the project-level config instead.

`sd config validate` MUST validate all discoverable config files (user-level, project-level, and per-VM) and report errors.

`sd config egress` MUST support the following subcommands:
- `sd config egress add <vm> <domain>` -- add a domain to a VM's egress allowlist
- `sd config egress remove <vm> <domain>` -- remove a domain from a VM's egress allowlist
- `sd config egress list <vm>` -- list the effective egress allowlist for a VM

**Acceptance criteria:**
- [ ] `sd config set defaults.backend lima` persists the value
- [ ] `sd config get defaults.backend` prints `lima` to stdout with no decoration
- [ ] `sd config list` displays all set configuration keys and values
- [ ] `sd config list --json` outputs configuration as a JSON object
- [ ] `sd config edit` opens the config file in the user's editor
- [ ] `sd config validate` reports validation results for all config files
- [ ] `sd config validate --json` outputs validation results as JSON
- [ ] `sd config egress add myvm custom.example.com` adds the domain
- [ ] `sd config egress remove myvm custom.example.com` removes the domain
- [ ] `sd config egress list myvm` shows all allowed destinations, distinguishing default from user-added
- [ ] `sd config egress list myvm --json` outputs the allowlist as a JSON array with a `source` field per entry

### REQ-002-006: Provisioning Commands

The `provision` command MUST support the following:

| Command | Syntax | Description |
|---------|--------|-------------|
| `provision` | `sd provision <vm> [--modules <list>]` | Run provisioning modules against a VM |
| `provision list` | `sd provision list` | List available provisioning modules |

`sd provision myvm` MUST execute all configured modules against the specified VM. `sd provision myvm --modules golang,rust` MUST run only the specified modules (plus their dependencies).

Modules are defined as YAML files: built-in modules are embedded in the binary (under `internal/provision/modules/`), and custom modules are YAML files placed in `~/.sd/provisions/`. There is no `provision add` subcommand; users add custom modules by creating YAML files directly. See spec 006 for module format details.

**Acceptance criteria:**
- [ ] `sd provision myvm` runs all configured modules against "myvm"
- [ ] `sd provision myvm --modules golang,rust` runs the specified modules plus dependencies
- [ ] `sd provision list` shows all available modules (built-in and custom)
- [ ] `sd provision list --json` outputs modules as a JSON array

### REQ-002-007: Diagnostic Commands

The following diagnostic commands MUST be implemented:

| Command | Syntax | Description |
|---------|--------|-------------|
| `doctor` | `sd doctor` | Check system prerequisites and report status |
| `version` | `sd version` | Print version, commit, and build info |
| `logs` | `sd logs [name]` | Show logs for a VM or for sd itself |

`sd doctor` MUST check for:
- Required binaries (lima/limactl, ssh, tmux, rsync)
- Network connectivity to required endpoints
- Valid configuration file
- VM backend availability

`sd doctor` MUST print each check with a pass/fail indicator (using simple unicode: checkmark or X).

`sd version` MUST print:
- Version string (semver)
- Git commit hash
- Build date
- Go version

`sd logs` MUST accept:
- `--tail <n>` -- show last N lines (default: 50)
- `--follow` / `-f` -- stream logs

**Acceptance criteria:**
- [ ] `sd doctor` checks for lima, ssh, tmux, rsync and reports each
- [ ] `sd doctor --json` outputs results as a JSON array of check objects
- [ ] `sd version` prints version, commit, date, and Go version
- [ ] `sd version --json` outputs version info as a JSON object
- [ ] `sd logs myvm --tail 20` shows the last 20 lines of VM logs

### REQ-002-008: Security Commands

The following security commands MUST be implemented:

#### Token Management

| Command | Syntax | Description |
|---------|--------|-------------|
| `token github setup` | `sd token github setup` | Guided setup for a fine-grained GitHub PAT |
| `token rotate` | `sd token rotate <vm>` | Rotate credentials for a VM |
| `token revoke` | `sd token revoke <vm>` | Revoke all stored credentials for a VM |
| `token list` | `sd token list <vm>` | List configured credential types (without values) |

`sd token github setup` MUST provide instructions for creating a fine-grained PAT with minimal scopes and MUST support `--json` to output recommended scopes as structured data.

`sd token rotate <vm>` MUST prompt for or accept new token values and update stored configuration.

`sd token revoke <vm>` MUST remove all stored credentials for the named VM. After revocation, `sd connect <vm>` MUST NOT inject any credentials.

`sd token list <vm>` MUST show which credential types are configured without revealing values.

#### Audit

| Command | Syntax | Description |
|---------|--------|-------------|
| `audit` | `sd audit [<vm>]` | Query the audit log, optionally filtered to a VM |

`sd audit` MUST accept:
- `--since <timestamp>` -- filter events after the given ISO 8601 timestamp
- `--json` -- output as a JSON array

#### Security Status

| Command | Syntax | Description |
|---------|--------|-------------|
| `security status` | `sd security status <vm>` | Display security posture summary for a VM |

`sd security status <vm>` MUST display: mount status, egress rules (count and list), credential types configured, snapshot count, and last audit event. Deviations from the recommended security posture MUST be flagged as warnings.

#### Diff

| Command | Syntax | Description |
|---------|--------|-------------|
| `diff` | `sd diff <vm>` | Highlight changes to CI/CD workflow files in the VM |

`sd diff <vm>` MUST detect changes to `.github/workflows/*`, `.gitlab-ci.yml`, `Jenkinsfile`, `.circleci/*`, and `.git/hooks/*` and flag them with warnings.

**Acceptance criteria:**
- [ ] `sd token github setup` outputs PAT creation guidance
- [ ] `sd token github setup --json` outputs recommended scopes as JSON
- [ ] `sd token rotate myvm` updates stored credentials
- [ ] `sd token revoke myvm` removes all credentials for the VM
- [ ] `sd token list myvm --json` shows credential types without values
- [ ] `sd audit myvm` displays audit log entries for the VM
- [ ] `sd audit --since 2026-03-27T00:00:00Z` filters by timestamp
- [ ] `sd audit myvm --json` outputs audit entries as a JSON array
- [ ] `sd security status myvm` displays security posture summary
- [ ] `sd security status myvm --json` outputs posture as structured JSON
- [ ] `sd diff myvm` highlights CI/CD file changes with warnings

### REQ-002-009: Command Aliases

The following command aliases MUST be registered:

| Command | Alias |
|---------|-------|
| `connect` | `c` |
| `list` | `ls` |

Aliases MUST appear in help text alongside the primary command name.

**Acceptance criteria:**
- [ ] `sd c myvm` is equivalent to `sd connect myvm`
- [ ] `sd ls` is equivalent to `sd list`
- [ ] `sd help` shows aliases in parentheses next to the primary command name

### REQ-002-010: Global Flags

The following global flags MUST be available on every command:

| Flag | Short | Default | Description |
|------|-------|---------|-------------|
| `--json` | | `false` | Output structured JSON to stdout |
| `--verbose` | `-v` | `false` | Enable verbose/debug output |
| `--quiet` | `-q` | `false` | Suppress all non-error output |
| `--config` | | `~/.sd/config.yaml` | Path to configuration file |
| `--vm` | | (from config) | Default VM name for commands that accept one |

`--verbose` and `--quiet` MUST be mutually exclusive. If both are provided, the CLI MUST exit with code 2 and a usage error.

`--vm` MUST serve as a default when a command expects a VM name argument but none is provided. If neither `--vm` nor a positional argument is given, the command MUST exit with code 2 and a clear error message.

**Acceptance criteria:**
- [ ] `--json` is recognized on every command
- [ ] `--verbose` and `-v` enable debug logging
- [ ] `--quiet` and `-q` suppress non-error output
- [ ] `sd --verbose --quiet` exits with code 2
- [ ] `--config /path/to/config.yaml` overrides the default config path
- [ ] `sd start` with `--vm myvm` set starts "myvm" without a positional argument
- [ ] `sd start` with no `--vm` and no argument exits with code 2

### REQ-002-011: Output Format -- Human-Readable

When `--json` is NOT set, commands MUST write human-readable output to the appropriate stream. Data-producing commands (e.g., `sd list`, `sd config get`, `sd ssh-config`) write to stdout. Progress messages, status updates, and informational text MUST go to stderr so that stdout remains clean for piping.

**Acceptance criteria:**
- [ ] `sd list` writes the VM table to stdout
- [ ] `sd config get defaults.backend` writes only the value to stdout
- [ ] `sd create myvm 2>/dev/null` produces no visible output (progress is on stderr)

### REQ-002-012: Output Format -- JSON

When `--json` is set, commands MUST write a single JSON object or JSON array to stdout. No other output (progress, warnings, banners) MUST appear on stdout. Warnings and debug messages, if any, MUST go to stderr.

The JSON output MUST conform to these conventions:

- Success response: `{"ok": true, "data": <command-specific>}`
- Error response: `{"ok": false, "error": {"code": "<error_code>", "message": "<human-readable>"}}`

**Acceptance criteria:**
- [ ] `sd list --json` outputs `{"ok": true, "data": [...]}` to stdout
- [ ] `sd create nonexistent --json` outputs an error JSON object to stdout
- [ ] `sd list --json 2>/dev/null` produces only valid JSON on stdout
- [ ] All JSON error responses include both `code` and `message` fields

### REQ-002-013: Exit Codes

The CLI MUST use the following exit codes:

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | General error (command failed) |
| 2 | Usage error (bad flags, missing arguments, invalid command) |

Exit code semantics MUST be consistent regardless of `--json` mode. When `--json` is active, the exit code MUST still reflect the outcome (0 for success, non-zero for failure), in addition to the JSON output.

**Acceptance criteria:**
- [ ] Successful commands exit with code 0
- [ ] Failed commands (e.g., VM not found) exit with code 1
- [ ] Invalid usage (e.g., unknown flag) exits with code 2
- [ ] `sd create --json` on failure exits with code 1 AND outputs error JSON

### REQ-002-014: Cobra Configuration -- Prefix Matching

Cobra prefix matching MUST be enabled so that unambiguous prefixes resolve to the full command. For example, `sd cre` MUST resolve to `sd create`, and `sd des` MUST resolve to `sd destroy`.

When a prefix is ambiguous (e.g., `sd co` matching both `connect` and `config`), Cobra MUST print an error listing the matching commands and exit with code 2.

**Acceptance criteria:**
- [ ] `sd cre myvm` is equivalent to `sd create myvm`
- [ ] `sd des myvm --force` is equivalent to `sd destroy myvm --force`
- [ ] `sd co` prints an ambiguity error listing `connect` and `config`

### REQ-002-015: Cobra Configuration -- PersistentPreRun

The root command MUST use `PersistentPreRunE` to perform the following before any command executes:

1. Load configuration from the file specified by `--config` (or the default path)
2. Validate mutual exclusivity of `--verbose` and `--quiet`
3. Initialize the logger with the appropriate verbosity level
4. Set up the output formatter (JSON or human-readable) based on `--json`

If configuration loading fails, the command MUST exit with code 1 and a clear error message. Commands that do not require configuration (e.g., `version`, `doctor`) MUST still succeed if the config file does not exist.

**Acceptance criteria:**
- [ ] Config is loaded before any command's `RunE` is invoked
- [ ] `--verbose --quiet` is rejected in `PersistentPreRunE` with exit code 2
- [ ] `sd version` succeeds even with no config file present
- [ ] `sd create myvm` with a missing config file exits with code 1 and explains the problem

### REQ-002-016: File Organization

Each command or command family MUST be defined in its own file under `internal/cmd/`. The root command MUST be in `internal/cmd/root.go`. The `Execute()` function MUST be exported from the `cmd` package.

Required files:

| File | Contents |

| `root.go` | Root command, global flags, `PersistentPreRunE`, `Execute()` |
| `create.go` | `sd create` command |
| `destroy.go` | `sd destroy` command |
| `start.go` | `sd start` command |
| `stop.go` | `sd stop` command |
| `list.go` | `sd list` command |
| `status.go` | `sd status` command |
| `snapshot.go` | `sd snapshot` and its subcommands |
| `connect.go` | `sd connect` command |
| `exec.go` | `sd exec` command |
| `sync.go` | `sd sync` and its `to`/`from` subcommands |
| `ssh_config.go` | `sd ssh-config` command |
| `config.go` | `sd config` and its subcommands (`set`, `get`, `list`, `edit`, `validate`) |
| `config_egress.go` | `sd config egress` and its subcommands (`add`, `remove`, `list`) |
| `provision.go` | `sd provision` and its subcommands |
| `token.go` | `sd token` and its subcommands (`github setup`, `rotate`, `revoke`, `list`) |

**Acceptance criteria:**
- [ ] Each file listed above exists in `internal/cmd/`
- [ ] Each file defines exactly one command or one command family
- [ ] `root.go` exports `Execute() error`
- [ ] No command registration logic exists outside `internal/cmd/`

### REQ-002-017: Shell Completions

The CLI MUST provide a `completion` command that generates shell completion scripts for bash, zsh, and fish.

| Command | Output |
|---------|--------|
| `sd completion bash` | Bash completion script |
| `sd completion zsh` | Zsh completion script |
| `sd completion fish` | Fish completion script |

The completion command MUST include usage instructions in its help text showing how to install the completion for each shell.

Custom completions MUST be registered for:
- VM name arguments (completing from the list of known VMs)
- `--backend` flag values (completing from available backends)
- Snapshot tag arguments (completing from existing tags for the specified VM)
- Provisioning module names (completing from registered modules)

**Acceptance criteria:**
- [ ] `sd completion bash` outputs a valid bash completion script
- [ ] `sd completion zsh` outputs a valid zsh completion script
- [ ] `sd completion fish` outputs a valid fish completion script
- [ ] VM name arguments offer tab completion from existing VMs
- [ ] `sd completion` help text includes installation instructions for each shell

### REQ-002-018: Error Serialization

All errors produced by the CLI MUST be serializable to JSON. The internal error type MUST carry:
- A machine-readable error code (string, `snake_case`, e.g., `vm_not_found`, `backend_unavailable`)
- A human-readable message
- An optional `details` field for additional context

When `--json` is active, errors MUST be output as:
```json
{
  "ok": false,
  "error": {
    "code": "vm_not_found",
    "message": "VM 'myvm' does not exist",
    "details": {}
  }
}
```

When `--json` is not active, errors MUST be printed to stderr in the format:
```
Error: VM 'myvm' does not exist
```

Error codes MUST use `snake_case`. All specs that define error codes MUST follow this convention.

**Acceptance criteria:**
- [ ] All command errors include a machine-readable code
- [ ] `--json` mode outputs the full error JSON structure to stdout
- [ ] Non-JSON mode prints `Error: <message>` to stderr
- [ ] Error codes use snake_case and are documented per command

### REQ-002-019: Default VM Resolution

When a command requires a VM name, the CLI MUST resolve it in this order:

1. Positional argument (e.g., `sd start myvm`)
2. `--vm` global flag (e.g., `sd start --vm myvm`)
3. Configuration default (`defaults.vm` in config file)

If none of these provide a VM name, the command MUST exit with code 2 and the message: `Error: no VM specified. Provide a name, use --vm, or set defaults.vm in config.`

**Acceptance criteria:**
- [ ] Positional argument takes precedence over `--vm` flag
- [ ] `--vm` flag takes precedence over config default
- [ ] Missing VM name in all three sources exits with code 2 and the specified message

### Root Command Setup

```go
package cmd

import (
	"github.com/spf13/cobra"
	"github.com/spf13/viper"
)

var rootCmd = &cobra.Command{
	Use:   "sd",
	Short: "Manage secure VM environments for AI coding agents",
	Long: `sd (secure-dev) creates, configures, and manages secure VM environments
for running AI coding agents with bypass permissions.

It automates VM lifecycle, SSH configuration, tool provisioning,
credential injection, and session management.`,
	SilenceUsage:  true,
	SilenceErrors: true,
	PersistentPreRunE: func(cmd *cobra.Command, args []string) error {
		// 1. Load config from --config path
		// 2. Validate --verbose / --quiet mutual exclusivity
		// 3. Initialize logger
		// 4. Set up output formatter (JSON vs human)
		return nil
	},
}

func Execute() error {
	return rootCmd.Execute()
}

func init() {
	// Global flags
	rootCmd.PersistentFlags().Bool("json", false, "Output structured JSON to stdout")
	rootCmd.PersistentFlags().BoolP("verbose", "v", false, "Enable verbose output")
```

### Output Formatter Interface

```go
package ui

// Formatter controls how command output is rendered.
type Formatter interface {
	// Success outputs a successful result. In JSON mode, wraps data
	// in {"ok": true, "data": ...} and writes to stdout. In human
	// mode, writes formatted text to stdout for data-producing
	// commands or to stderr for progress/status.
	Success(data any)

	// Error outputs an error. In JSON mode, writes
	// {"ok": false, "error": {...}} to stdout. In human mode,
	// writes "Error: <message>" to stderr.
	Error(err CLIError)

	// Progress writes a progress message. In JSON mode, this is a
	// no-op on stdout (may write to stderr if --verbose). In human
	// mode, writes to stderr.
	Progress(msg string)

	// Warn writes a warning message to stderr in both modes.
	Warn(msg string)
}
```

### VM Name Resolution Helper

```go
package cmd

// resolveVMName determines the VM name from args, flags, or config.
// It returns the name or an error with exit code 2.
func resolveVMName(cmd *cobra.Command, args []string) (string, error) {
	// 1. Positional argument
	if len(args) > 0 && args[0] != "" {
		return args[0], nil
	}

	// 2. --vm flag
	if vm, _ := cmd.Flags().GetString("vm"); vm != "" {
		return vm, nil
	}

	// 3. Config default
	if vm := viper.GetString("defaults.vm"); vm != "" {
		return vm, nil
	}

	return "", CLIError{
		Code:    "no_vm_specified",
		Message: "no VM specified. Provide a name, use --vm, or set defaults.vm in config.",
	}
}
```

## Error Handling

### Error Categories

| Category | Behavior | Example |
|----------|----------|---------|
| Fatal | Print error, exit with code 1 | VM backend not available, SSH connection refused |
| Usage | Print usage hint, exit with code 2 | Unknown flag, missing required argument |
| Warning | Print warning to stderr, continue | Config file not found (for commands that don't require it) |

### Error Codes

The following error codes MUST be used consistently. All codes use `snake_case`.

#### VM Management Errors

| Code | Trigger | Exit Code |
|------|---------|-----------|
| `vm_not_found` | Named VM does not exist | 1 |
| `vm_already_exists` | Creating a VM with a name already in use | 1 |
| `vm_not_running` | Command requires a running VM but it is stopped | 1 |
| `vm_already_running` | `start` on an already-running VM | 1 |
| `backend_unavailable` | Required backend (e.g., lima) is not installed | 1 |
| `snapshot_not_found` | Named snapshot does not exist | 1 |
| `snapshot_failed` | Snapshot creation failed (e.g., insufficient disk space) | 1 |

#### Configuration Errors

| Code | Trigger | Exit Code |
|------|---------|-----------|
| `config_invalid` | Configuration file is malformed | 1 |
| `config_not_found` | Configuration file does not exist (when required) | 1 |
| `config_write_failed` | Failed to write configuration file | 1 |

#### Connection Errors

| Code | Trigger | Exit Code |
|------|---------|-----------|
| `ssh_connection_failed` | Cannot establish SSH connection to the VM | 1 |
| `ssh_auth_failed` | SSH key authentication failed | 1 |
| `ssh_timeout` | SSH connection timed out | 1 |
| `port_in_use` | Forwarded port is already in use on the host | 1 |
| `sync_failed` | File sync operation failed | 1 |

#### Provisioning Errors

| Code | Trigger | Exit Code |
|------|---------|-----------|
| `provision_failed` | A provisioning module failed to execute | 1 |
| `provision_script_failed` | A specific script within a module failed | 1 |
| `module_not_found` | Specified module does not exist | 1 |
| `module_dependency_cycle` | Circular dependency in module declarations | 1 |
| `probe_timeout` | Readiness probe timed out | 1 |

| Code | Trigger | Exit Code |
|------|---------|-----------|

## Security Considerations

- **No secrets in CLI arguments.** The CLI MUST NOT accept tokens, passwords, or secrets as flag values or positional arguments. Secrets are injected via environment variables or configuration files with restricted permissions. Command-line arguments are visible in process listings.
- **Config file permissions.** When the CLI creates or writes the configuration file, it MUST set permissions to `0600` (owner read/write only).
- **No shell expansion in exec.** `sd exec` MUST pass commands directly to SSH without shell interpolation on the host side. The `--` separator ensures arguments are not interpreted as flags.
- **Audit logging.** All state-changing commands (`create`, `destroy`, `start`, `stop`, `snapshot restore`, `provision`, `config set`, `token rotate`, `token revoke`, `config egress add`, `config egress remove`) SHOULD be logged with timestamps for auditability.
- **Blast radius.** The CLI itself runs on the host. A compromised CLI binary could access host resources. Binary integrity should be verified via checksums on distribution. The CLI does not handle credentials directly; it delegates credential injection to the provisioning and session subsystems.

## Testing Strategy

### Unit Tests

- **Flag parsing**: Verify all global and command-specific flags are parsed correctly, including mutual exclusivity of `--verbose`/`--quiet`.
- **VM name resolution**: Test the three-tier resolution (positional > `--vm` > config default) and the error case.
- **Output formatting**: Test that `Formatter.Success`, `Formatter.Error`, and `Formatter.Progress` produce correct output in both JSON and human modes.
- **Error serialization**: Test that `CLIError` serializes to the expected JSON structure with `snake_case` error codes.
- **Command registration**: Test that all commands are registered, aliases work, and groups are assigned.

### Integration Tests

- **End-to-end command execution**: Run `sd create`, `sd list`, `sd destroy` against a real (or mocked) backend and verify exit codes and output.
- **Config round-trip**: `sd config set` followed by `sd config get` returns the set value.
- **JSON output validation**: Parse JSON output from every command with `--json` and validate against expected schema.
- **Exit code verification**: Verify exit codes for success, failure, and usage error scenarios.
- **Security commands**: Verify `sd token list`, `sd audit`, `sd security status`, and `sd config egress list` produce correct output.

### Script Tests

- **CLI workflow scripts**: Script-driven tests (rsc.io/script or shell scripts) that exercise full workflows:
  - Create, connect, exec, snapshot, destroy lifecycle
  - Config set/get/list round-trip
  - Doctor checks with and without prerequisites
  - Error scenarios (missing VM, invalid flags)
  - Token management lifecycle (setup, rotate, list, revoke)
  - Egress management (add, list, remove)
  - Sync to/from file transfer
- **Completion tests**: Verify that generated completion scripts are syntactically valid for each shell.
